# hbc-decompiler

A decompiler for Hermes bytecode (HBC) **version 98**. It turns a `.hbc` file
back into readable, runnable JavaScript, and can also print a disassembly.

It is a self-contained Python 3 tool with no dependencies; it does not need a
Hermes build.

```bash
tools/hbc-decompiler/hbc-decompile app.hbc -o app.js
```

```bash
tools/hbc-decompiler/hbc-decompile --disassemble app.hbc
```

## Which "version 98"?

The v98 opcode set changed several times without a version bump (between
`c00cc5759`, Aug 2024, and `42235b8d9`, Feb 2026). The shipped opcode tables
(`hbcdecompiler/tables.py`) match the **last** v98 commit, `639e5d6af`, the
parent of "Bump bytecode version to 99". For a file produced by an earlier v98
compiler, regenerate the tables from a checkout of that compiler's source:

```bash
python3 tools/hbc-decompiler/hbcdecompiler/gen_tables.py /path/to/hermes > tools/hbc-decompiler/hbcdecompiler/tables.py
```

The file header, function headers, string tables, literal buffers and debug
info layout are the same across those snapshots.

## What the output looks like

- **Expressions are rebuilt** from the register code: temporaries are inlined
  back into expression trees, while side effects stay in their original order.
  Copy and constant propagation remove register moves, and object/array
  literals (including getters/setters, computed keys and spreads), `new`
  expressions, method calls, template literals, `&&`/`||`/`??`, ternaries and
  `f(...args)` spreads are reconstructed.
- **Control flow is structured** into `if`/`else`, `while`/`do`/`for (;;
  update)`, `for…in`, `for…of`, `switch` (including dense and string switch
  tables), `try`/`catch`, labeled `break`/`continue` and labeled blocks. A
  function whose control flow cannot be expressed with these constructs is
  emitted as an equivalent `for (;;) switch (_pc)` dispatch loop (marked
  `(unstructured)` in its header comment), so the output stays correct.
- **Closures are nested** at the place where they are created. Captured
  variables (Hermes environments) become `let` variables named
  `e<env>_<slot>`. Environments created inside loops keep their per-iteration
  scope when that is safe.
- **Naming**: parameters are `a0, a1, …`, registers are `r0, r1, …`, and
  globals and properties keep their names. Function names come from the
  bytecode. Each function starts with a `// #<id> <name>` comment, which can be
  turned off with `--no-annotate`.
- `"use strict"` is emitted for strict functions. Non-constructible functions
  that do not use `this`, `arguments` or `new.target` are printed as arrow
  functions.
- **Runtime helpers**: Hermes operations with no JavaScript syntax equivalent
  are calls to a small `$hbc` helper object (generator objects, async
  functions, classes, private fields, `for…in`/`for…of` plumbing that could not
  be turned back into loops, Hermes builtins such as `copyDataProperties`). Its
  definition (`hbcdecompiler/prelude.js`) is prepended to the output when
  needed, so the output runs as is.
- Generators and async functions are compiled by Hermes v98 into state
  machines. They are decompiled as those state machines, wrapped by
  `$hbc.createGenerator` / `$hbc.spawnAsync`, rather than as `function*` /
  `async function`.
- Classes are rebuilt with `$hbc.createClass` and `Object.defineProperty` for
  methods, rather than as `class` syntax.

## Layout

| File | Purpose |
| --- | --- |
| `hbcdecompiler/reader.py` | HBC file parser (headers, strings, literal buffers, bigints, regexps, CJS tables, debug info) |
| `hbcdecompiler/tables.py` | Opcode and builtin tables, generated by `gen_tables.py` |
| `hbcdecompiler/disasm.py` | Instruction decoding, switch tables, literal buffers, text disassembly |
| `hbcdecompiler/lifter.py` | Instructions to a flat register IR; basic blocks; environment and closure tracking |
| `hbcdecompiler/dataflow.py` | Liveness, copy/constant propagation, order-preserving expression folding, literal reconstruction, dead code elimination |
| `hbcdecompiler/structure.py` | CFG analysis (dominators, loops) and control flow structuring, plus the dispatch-loop fallback |
| `hbcdecompiler/decompiler.py` | Driver: per-function pipeline, closure nesting, AST cleanups, scoping and printing |
| `hbcdecompiler/jsast.py` | JavaScript AST and pretty printer |
| `hbcdecompiler/prelude.js` | Runtime helpers referenced by the output |

## Testing

`tests/run_tests.py` compiles every program in `tests/corpus/` with a v98
`hermesc` at `-O` and `-O0`, decompiles the bytecode, runs both with a v98
`hermes`, and checks that the outputs are identical:

```bash
git worktree add /tmp/hermes-v98 639e5d6af
```

```bash
cmake -S /tmp/hermes-v98 -B /tmp/hermes-v98-build -G Ninja -DCMAKE_BUILD_TYPE=Release -DHERMES_UNICODE_LITE=ON
```

```bash
cmake --build /tmp/hermes-v98-build --target hermesc hermes
```

```bash
python3 tools/hbc-decompiler/tests/run_tests.py --bin /tmp/hermes-v98-build/bin
```

`tests/fixtures/` holds precompiled v98 bytecode with the expected program
output, so the tool can be checked without building v98, using Node.js to run
the decompiled code:

```bash
python3 tools/hbc-decompiler/tests/run_fixtures.py
```

The same round trip was run on the v98 `test/hermes` suite and on the Octane
benchmarks. For most of the remaining differences the program inspects its own
source: stack traces and line numbers, `Function.prototype.toString`, function
`name` and `length`, or error message text. Octane programs check their own
results. At `-O`, richards, deltablue, raytrace, crypto, navier-stokes, splay,
regexp, box2d, gbemu, typescript and pdfjs pass after decompilation (earley-boyer
does not, see Limitations; it passes at `-O0`), including typescript (2.5 MB of source, 1,561
functions, about 6 seconds to decompile) and pdfjs (one function holding
1.1 MB of bytecode, about a minute).

## Limitations

- Local variable names are not stored in HBC, so registers and environment
  slots get synthetic names.
- Temporal dead zone checks (`ThrowIfEmpty`) are dropped: reading a `let`
  before its initialization yields `undefined` instead of throwing.
- `Inc`/`Dec` on BigInt values are printed as `x + 1`/`x - 1`, which throws for
  BigInts.
- When the optimizer inlined a function into itself, creating new closures of
  the function being inlined, the inner closures are printed as references to
  the outer function. Their environments can differ from the original.
- When an inlined closure reads another function's local environment, the
  variables are out of lexical scope in the output.
- The generator objects returned by `$hbc.createGenerator` are not real
  `Generator` instances (`instanceof` and the prototype chain differ).
- Functions that fall back to the dispatch loop run correctly but slowly. In
  the zlib Octane benchmark (Emscripten output) a few hot functions take this
  form, and the decompiled program ran for over 30 minutes without finishing,
  against about 70 seconds for the original bytecode.
- Delta-form ("delta prepped") bytecode is not supported.
